# Conformance corpus (spec version 0.1)

Implementation-independent test cases for the AMPLE language. Any parser, formatter or language server can run them. Layout:

| Folder | Files | Rule |
| --- | --- | --- |
| `valid/` | `NAME.amplet`, `NAME.expected.json` | no `error` diagnostics; `expected.json` lists the project, the blocks (type, name, class, version) and the non-error diagnostics |
| `invalid/` | `NAME.amplet`, `NAME.expected-diagnostics.json` | the diagnostics (code, severity, line, col, endCol, message) must equal the file, **compared as a set sorted by (line, col, code)**; the name starts with the code the case demonstrates |
| `recovery/` | `NAME.amplet`, `NAME.expected.json` | broken input; the parser must keep the listed blocks and report the listed codes |
| `format/` | `NAME.in.amplet`, `NAME.out.amplet` | formatting `in` gives exactly `out`; formatting `out` changes nothing |
| `roundtrip/` | `NAME.amplet` | canonical files: parse then print gives the same bytes |
| `parity/` | scenario files | UI parity (chunk 05), not language |

Messages are compared too, but a message change is a deliberate, reviewed change ([maintenance](../docs/language/99-maintenance.md)).

**Origin:** `valid/`, `invalid/` and `recovery/` were generated by `tools/gen-corpus.mjs` with the sketch's mock parser as the oracle. `format/` and `roundtrip/` are hand-written. From chunk 20 on the corpus is edited by hand and is the oracle. Check the structure with `node ample/tools/validate-spec.mjs`.
