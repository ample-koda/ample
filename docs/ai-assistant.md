# The AI assistant (Codex)

### Playback and request responsiveness (2026-10-17)

Sample cards request serialized, small server-side waveform summaries instead of downloading and decoding each full song in the browser. Stop releases the audio source. Task indicators do not poll behind an open conversation and never overlap their own requests; closing a conversation aborts its pending poll. Read requests have a 15-second timeout. Hidden tabs release their event stream and reconnect when visible, leaving browser connections available for controls. The source context menu does not wait for AI status before showing ordinary editing actions. These safeguards address verified unbounded requests and full-song waveform downloads; actual delays still need the browser's Timing view to distinguish connection queueing from server work.

### Long tasks and recovery (2026-10-17)

Codex turns have no fixed twenty-minute wall-clock cutoff. Explicit Stop and cancellation remain available; the existing inactivity probe checks silent turns. Failed tasks, including older twenty-minute timeouts, can resume their saved Codex thread once the previous worker has ended, provided the task workspace still exists. Resume retains the working copy and delivered samples; it does not restart the original request from scratch.

### Accept and bounded Continue (2026-10-10)

**Accept selected** applies only the checked files and starts no Codex turn. **Accept selected & continue remaining** is a separate explicit action. **Continue remaining work**, including after a samples-only answer, resumes the same conversation and supplies a checkpoint of the original request, user requirements, accepted files, existing clips and last answer. It does not reject the task and reopen the original prompt. Closing the samples-only window leaves the conversation intact.

Continue preserves delivered work and quantity requirements. For an unambiguous request containing one numeric sample/clip/variant count (or five/vijf), the server counts proposal clips delivered for that request; current-project reference clips are excluded. A clear later sample request in user messages supersedes the earlier quantity. If that count is met, Continue starts no turn. Otherwise the presentation endpoint enforces the remaining count for that continuation, including concurrent calls. Multiple quantities or other wording are retained in the checkpoint but are not inferred as a machine-enforced numeric quota. A new explicit sample request via Send (for example “give me 5 more samples”) clears the continuation quota; ordinary feedback does not.

Buttons suppress repeat clicks, and the server serializes review actions and rejects Continue when a turn is already running. The quota and presented clips persist with the task. Source/build checks are separate from real-Codex/browser acceptance, which remains pending.

### Temporary listening trials (2026-10-10)

AI clip waveforms show the maximum magnitude across all audio channels. Quiet waveforms are scaled for visibility (up to 1000× visual magnification); this does not change playback gain, and waveform height should not be used to compare absolute loudness. Silent audio stays a flat line.

POST context routes for edit, listen, present, and staged moves (`move`, `move-file`) authenticate with a registered `X-Ample-Context` task token. They do not require the browser's session token in addition; unknown/missing task tokens do not grant access. Host/origin checks still apply. When adding a new POST context tool, update both its route/MCP call and the exact authorization allowlist in `AmpleServer.cs`.

`ample_present` accepts optional `path` and `edits`, using the structured `ample_edit` format. For example, present the master with `source=proposal`, `from="0"`, `to="30"`, and `edits=[{"op":"set_param","block":"wonderwall-guitar","name":"program","value":"24"}]`. Repeat with programs 25 and 26 for real instrument comparisons. The edits apply only in the temporary render project; the proposal and live project remain unchanged. `source=current` rejects trial edits. Apply the winning settings with `ample_edit` afterwards.

The tool returns parsed source `settings`, the applied `trial` summary, `audioHash` and `identicalTo` when another presented clip contains the same canonical WAV bytes. Exact equality proves matching audio; different hashes do not prove a perceptible difference. The card exposes these source settings and warns about identical audio. Clips and metadata are saved with the task and restored after restart. Audio is captured inside the render lock, avoiding another listen call replacing its temporary take before presentation. Labels and descriptions never change audio. Bars use the rendered source tempo.

Activity and sample lists forward excess wheel scrolling to the outer task page at their top and bottom boundaries. Browser and real instrument comparison acceptance remains pending.

Status (2026-10-09): built, optional, off by default. Codex **proposes**, AMPLE **validates**, the user **decides**.

## Inspect tool activity

AI dialog headers expose an icon-only Stop music button just before Close while project or proposal playback is active. It stops both players without cancelling a build or the AI task, then disappears. Its active styling matches the master Stop control.

Starting a full-song build stops project and proposal playback automatically, including a full proposal build. Build-and-play/build-and-listen still starts the resulting audio after building.

Each tool or command activity row has a small ↗ button opening a full-screen detail dialog. It shows the timestamp, input, output, errors and original MCP/command metadata as plain text. New operation payloads are saved with the session; older summary-only entries explicitly say their payload was not captured. Batch calls are expandable individually, with ordered input/result pairs and error flags; the original combined response remains available. The MCP batch result preserves its text response and also exposes structured results (at most 12 executed calls). No extra tool execution occurs when inspecting a call.

Samples in Output can be marked obsolete by the user with a reason, or by Codex with `ample_obsolete_sample` when later edits make a prior render unrepresentative. Obsolete cards remain in place, dimmed, and show the reason; only the × dismisses them from the view.

The updated server must be started before new payloads can be captured. This does not recover details already discarded by an older server.

## Two kinds of approval

New staged songs and blocks can be read before acceptance. When editing an existing project file not initially copied into the proposal, the editor uses its current disk text as the baseline; replacements are not applied to an empty string. Explicit owner workflow exceptions apply within the scope authorized in the conversation, subject to actual tool/sandbox permissions.

1. **Codex action approval** (what Codex may do while it works): the project setting *execution mode*.
2. **Proposal acceptance** (whether the result becomes part of the project): always the user, in the proposal wizard. Even *Unsafe / Auto-all* never accepts anything for you.

## Server and project

The **server** says what a project MAY choose (`%LOCALAPPDATA%\ample\ai-policy.json`, or the AI settings dialog > *Server capabilities*): Codex enabled, the server-user account, project Device ID identities, inheriting the system-user configuration, and each of Manual, Auto and Unsafe. All are on by default. If something is turned off, a project that uses it shows as unavailable; nothing falls back to another identity or mode. Optional fields `model`, `effort` and `codexPath` (and the environment variables `AMPLE_CODEX_MODEL`, `AMPLE_CODEX_EFFORT`) choose the Codex model and reasoning effort.

The **project** chooses (`project.json`, `settings.ai`): the assistant (*No AI assistant*, *Codex - Server account*, *Codex - Project Device ID*) and the execution mode. The default of a new assistant is **Auto**. The first use needs an acknowledgement of the risks, and the first time for Unsafe another one. The settings never contain a secret.

| Mode | Codex's own approval and sandbox | What it means |
|---|---|---|
| Manual | `approvalPolicy untrusted`, `workspace-write` | reads freely, asks before it writes or changes anything; each request is shown to you |
| Auto | `on-request`, `workspace-write` | Codex decides what is routine and asks for the rest |
| Unsafe / Auto-all | `never`, `workspace-write` | nothing is asked: what the sandbox allows runs at once, what it does not allow is refused |
| (any mode, a request to *explain*) | `never`, `read-only` | Codex cannot write at all |

Codex only ever needs to write in its own temporary copy, so **the sandbox stays on that copy in every mode**. Only if the server administrator turns on `unsafeNoSandbox` (off by default, AI settings > Server capabilities) does Unsafe / Auto-all use `danger-full-access`.

A denied request is respected; modes are never raised by themselves. Lowering the mode applies at once; raising it is an explicit choice.

## Identities (what Codex really supports, checked on Codex 0.160)

- **Server account**: the Codex login of the user the server runs as (its `CODEX_HOME`). Its configuration and global `AGENTS.md` live in the same home as the login and cannot be separated from it; with inheritance switched off on the server AMPLE only switches off `AGENTS.md` files of the project (`project_doc_max_bytes=0`) and says so.
- **Project Device ID**: its own `CODEX_HOME` (`%LOCALAPPDATA%\ample\codex-homes\<project id>`, outside the project), linked with the real device flow (`account/login/start` of the Codex app server: an address and a code). Nothing of the user's Codex is read or changed. *Link*, *Re-authenticate* and *Unlink* are in the settings. The login is never part of the song, a package or Git.
- One Codex account is used by one task at a time (its refresh token works once). Further tasks **wait in a queue** (the wizard says how many are ahead; a queued task can be cancelled) behind a lock file per account in `%LOCALAPPDATA%amplecodex-locks`, so it holds across projects and servers.

## A task

AMPLE copies the files in scope (text files only) into `.ample/ai/work/<task>/project` with the reference, a `TASK.md`, an `AGENTS.md` and the skill `ample` (`.agents/skills/ample`), starts the **Codex app server** there (JSON-RPC over stdio), and gives Codex a read-only MCP server `ample` (the command `ample mcp`, with a token of this task that can only read): `ample_project`, `ample_faer_status`, `ample_docs`, `ample_block_types`, `ample_song`, `ample_block`, `ample_file`, `ample_analyze` (tempo, key, loudness, spectrum, pitch of a built block) and `ample_request_asset`. `ample_faer_status` reports the project's independent song/voice/separation routes, live capability readiness and the current ACE `.gguf` filenames, roles and sizes; it returns no credentials or job content. The ACE model catalog explains model roles and recommendations. Codex keeps AMPLE's hardcoded family choices, combines them with live server offers, and can use the exact-file field for a server-listed unfamiliar variant. When relevant, the final proposal summary names the model choice so it is visible on Output, Changes and Checks.

The `ample_project` response lists task-work files separately under `taskWorkFiles`. On path-based read calls such as `ample_file`, `ample_song` and `ample_block`, pass `location=work` to read one of those files; `location=project` (the default) reads the normal project file. The `path` stays a plain relative filename. Hidden internal files and `rpc.log` are excluded, and choosing `location=work` is read-only. The task composer has an unchecked **Strict mode** option. Off by default, Codex can ask for approval before accessing files or running commands outside its task work folder; the request is surfaced in the task UI and waits for the user's decision. When checked, the current strict policy applies. This is separate from the manual/auto/unsafe interaction choice: non-strict always uses sandboxed, on-request permissions so an external request cannot be silently refused or silently granted.

For every `.amplet` containing `ace-music` or `ai-voice`, Codex must write `settings { acestep.backend server }` in that song, including baselines and every standalone variant. A project default is insufficient; missing it produces AMP2013 and prevents the ACE block from building with AMP5370. Apply the setting identically across seed-comparison files before rendering. This selects the ACE server backend; the project's separate local/Faer capability route decides where the request is sent. Resolve this preflight error before investigating Faer readiness, model loading or VRAM. Submit Faer renders sequentially so one GPU job owns the model load/render/release cycle at a time, and call `ample_present` immediately after each successful render before starting the next. This makes each playable sample available while later variants are still rendering; do not wait for the whole batch before presenting the first one.

When Codex is done, AMPLE compares the copy with the baseline and shows: what Codex says, the changed files with a diff, the diagnostics, the build result (the proposal is built in a staged copy of the project, so you can listen to it) and warnings. The fixed tab row stays above each tab's scrollable content: the written summary appears in Output, Changes and Checks, while the newest presented sample is first in Output. The preview target follows the song Codex actually rendered or measured, including when a proposal adds multiple songs; the proposal window names that target, and **Look at it in the block view** opens that proposed song read-only while the project keeps its active song. A failed or refreshed proposal clears the prior build audio, and a lost task connection pauses playback and hides output until the newest task result is confirmed. If the user explicitly asks for no build or render, Codex calls `ample_skip_build`: AMPLE still checks source errors and warnings, labels the proposal **Build not run (as requested)** with the reason, and allows Accept without waiting for a build. The user can still choose **Build and test again**. **Accept** is refused when source errors exist or a build fails; **Accept anyway** applies a failed build (unsaved, undoable) after a clear warning. Accepting makes a checkpoint first, writes other files through the journal (undoable from the wizard) and applies the song as one undo step in the editor. If the project changed while Codex worked, the proposal is not applied blindly: *Try to rebase* (a three-way merge, conflicts are reported), *Regenerate*, or *Review anyway* (view only).

### Sampling ACE/Faer seeds

When the user wants to compare generated voices or performances across seeds, treat it as an audition: Codex presents the candidates and the **user chooses**; Codex must not pick a winner on the user's behalf. Keep lyrics, prompts, model, inference settings, arrangement and all other song settings fixed so the seed is the only intentional difference.

When a genuinely random master or block seed is needed, call the MCP tool `ample_random_seed`. It uses the operating system's cryptographic random generator and returns a positive 64-bit value accepted by AMPLE; do not ask the language model to invent a supposedly random number.

An unverified baseline is not a reason to refuse a requested song or render batch. Create the requested first version, render it with AMPLE's build/listen tools, then continue through the requested number of candidates and present the resulting samples. A missing baseline limits claims about comparative quality, not the ability to generate. Distinguish source checks and measured audio facts from subjective musical quality; do not claim a render succeeded until AMPLE confirms it. Shell builds remain out of scope: use the integrated AMPLE tools, and skip rendering only when the user explicitly asks for no build or render.

### Lyrics files in generated songs

Choose the lyric format for the request. For exact, untimed lyrics supplied for ACE music generation, preserve them in `.txt` and feed them through the lyrics block; `.txt` is an accepted lyrics source and avoids inventing bar timings. Use `.lyr` when the owner wants AMPLE's timed-lyrics workflow or Lyrics editor: one `[bar N] text` row per lyric line, stored in `lyrics/<name>.lyr`, referenced by a `lyrics` block whose `words` output connects to ACE music or AI voice. Preserve the user's words exactly; do not convert untimed lyrics to `.lyr` unless timing is requested or clearly useful and can be added without changing the words.

There are two valid ways to do this:

- **Separate files:** derive each standalone `.amplet` from the same baseline, change only the relevant seed value(s), and build/render each file. Use this when the user wants reproducible variants they can keep and revisit.
- **Sequential samples:** keep one song and its settings fixed, set one candidate seed, request a preview/output sample, then change only the seed and request the next sample. Keep each presented sample available and identify it by its seed value(s), so the user can compare them and choose. After the user chooses, put the chosen seed value(s) in the retained song.

Do not claim that a candidate was generated or rendered until its build or preview actually succeeds. If the current tools, project route or server cannot render the requested candidates, explain that limitation and offer the other route; never fabricate sample results or imply that changing a seed alone rendered audio.

**Large or non-text assets** (a sample, a recording) are not copied up front. Codex asks with `ample_request_asset` (path and reason); the wizard shows the request (kind *asset*, with the size) and in Manual and Auto the user allows or denies it; in Unsafe it is allowed at once. When allowed, AMPLE copies the file into `assets/<path>` of the task's copy and tells Codex where it is. Assets are outside `project/`, so they never show up in the proposal.

Autocomplete (`Ctrl+Space`, the grey suggestion) stays local and never calls Codex.

`ample_redux_search` is a read-only MCP tool and starts in the current task's AMPLE Redux archive. Codex can explicitly select its current session or expand to project history. Results are paged; payloads stay hidden unless one AR record is requested in detail.

## Server policy cannot be widened by a project

`/api/ai/policy` is reachable with the token of a project, and the token of a project is not the administrator of the machine. So over the API the policy can only be **tightened**: a capability can be switched off, never on, `unsafeNoSandbox` can be switched off but never on, and the program that is started as Codex (`codexPath`) cannot be changed at all (error AMP5459). Allowing more is done by editing the policy file `%LOCALAPPDATA%ampleai-policy.json` (or setting `AMPLE_CODEX`), which requires access to the machine. The settings page shows a switch that is off as disabled, with that explanation.

## "Changeset only": what it is and why it is not a separate mode

The idea (owner, 2026-10-09): Codex starts with **no ability to write anywhere** and its output is a **changeset** (a list of file changes) that AMPLE shows, checks and applies after approval.

What exists instead, and why it comes to the same thing for the project:

- Codex runs in a **temporary copy** (`.ample/ai/work/<task>/project`), with its sandbox on that copy in every mode (`workspace-write`; `read-only` for a request that only asks to explain). It cannot write to the real project. AMPLE then computes the changeset itself by diffing that copy against the baseline taken at the start (the *Changes* tab), checks it (parse, staged build) and applies it only when you press Accept (one undo step for the song, the journal and a checkpoint for other files).
- So the **effect** is the one asked for: nothing in the project changes until Accept, and what Accept applies is exactly the shown changeset.
- What is **not** the same: Codex does write files, but in the throw-away copy. A true "changeset only" mode would need Codex to run with a read-only workspace and return its edits as structured output (a patch) instead of editing files. Codex's own tools for editing are file based and its sandbox modes are `read-only`, `workspace-write` and `danger-full-access`, so a patch-returning flow means asking the model to output patches as text and parsing them, which is less reliable for multi-file work and gives up Codex's own run-and-check loop. It is therefore **not built**; the only read-only use is the *explain* request.
- If it is ever built, it should be a fourth choice next to Manual, Auto and Unsafe (not a replacement), with the same checks and the same Accept step, and the changeset format should be a unified diff per file (the format AMPLE already shows and applies).

## What the user sees while Codex works

- **Tool use is shown with its arguments and elapsed time**, for example `ample_build (block=mix): completed · 12.4 s`; a failed call shows Codex's own error text. The proposal's automatic build check also reports its elapsed time.
- Build, listen and arrangement-measure tools follow the project's configured routes, including Faer. Avoiding Faer-specific tool calls does not force local rendering. There is no per-call local-only override yet; if a user asks to avoid Faer while a route is set to Faer, Codex must say that it cannot guarantee local rendering.
- **A thinking bubble.** Codex can tell you what it is thinking about with the MCP tool `ample_thinking`, and every other tool takes an optional `thinking` argument that does the same. The latest thought is shown as a speech bubble with the two before it faded, beside an animated badge; thoughts are also kept in the Activity log. The title bar also shows a blinking activity dot and the current action while Codex works or AMPLE checks the proposal. Activity visually distinguishes what the user sent, Codex's notes and its answer, while tool details are quieter. Changed files appear in a highlighted, clickable group, and `ample_edit` can include an optional per-file `why` shown beside its diff. Audio cards can be hidden one at a time and restored with Ctrl+Z until the proposal window is closed. These are notes written by the model, not a view into its reasoning.
- **A document that does not exist is not an error:** `ample_docs` accepts the name with or without `docs/` and `.md`, and for an unknown name it answers with the closest document names (`didYouMean`). Earlier, a wrong guess showed up as a failed tool call.
- The task window keeps its scroll position while it updates and the log follows its end.
- In an active task, the proposal header identifies the task's actual Codex account and mode; it does not reuse a possibly stale project-settings badge. Sample playback continues while task updates redraw the conversation. Temporary refresh errors show a reconnecting notice and retry while preserving the current view.
- Newly proposed files are absent from the live baseline until accepted. Stale checks treat those paths as absent instead of trying to open them as existing song documents.

## Look at a proposal in the real views and build it

AI proposal builds can use the active project's takebank as an additional read-only audio cache. This is on by default in **Project settings > AI assistant** and can be turned off there. Only exact plan-id matches are reused, so source, effective settings, seeds, inputs and renderer identity must all match. Matching blobs and any required parent-plan records are copied into the temporary proposal takebank for downstream rendering; the active project's takebank is never changed.

If a current-project sample sounds inconsistent with the current song, or a frozen selected take could hide the requested localized change, Codex should diagnose it autonomously with `ample_present` using `source=current` and `rebuildCurrent=true`. AMPLE rebuilds from current song text in a temporary project while bypassing selected-take choices and preserving pinned melody choices. When the exact plan already exists in the active project's read-only takebank cache, AMPLE reuses that audio; otherwise it renders the current plan. Codex compares the returned take id, plan id, audio identity and audible scope with the ordinary current sample, then uses that evidence to correct its proposal without asking the user to find cache or take ids. The clip is labeled **rebuilt from current song text**; the active project and its takebank remain unchanged.

- **Look at it in the block view** (button at the bottom of the proposal window): the proposed song is shown read-only in the real Blocks view (the same canvas, panels and properties as for your own song), with a yellow banner and the badge *peek: AI proposal*. Nothing is saved or changed; clicking the banner goes back to the proposal. It is the same read-only *peek* that the history uses for an old state. The build marks you see there (cache hit, waveforms) are those of your current project, not of the proposal.
- **In that preview the normal controls work on the proposal, never on your project:** the **Build** button and the Play button of the header build the whole proposal in its temporary project and play the master, every audio block has a small ▶ that builds that block (and what it needs) and plays it, and the blocks show their build result (built, failed). Your own takes are not shown there and nothing of your project is built, overwritten or saved. A built block gets a normal audio player (play, scrub, repeat) that reads from the temporary project of the proposal, so listening again needs no new build; the temporary project is kept while the proposal does not change.
- **Build and listen to one block:** right-click a block in that preview > *Build and listen to this block (AI proposal)*. AMPLE builds that block and what it needs in the temporary project of the proposal and plays the result.
- **Build and test the whole proposal:** the *Checks* tab has *Build and test again*, which builds the proposal in the temporary project and plays the master. The first check still runs when the proposal is ready; a build you ask for waits for it. API: \`POST /api/ai/tasks/{id}/build\` (optional \`block\`), \`GET /api/ai/tasks/{id}/text\` and \`/audio\`.

## Going on before you accept: quick iteration

- **The Codex session stays open** after the first answer, until you accept or reject (or when the server stops). It ends after 30 minutes without a message (the proposal itself stays). You then choose: **Resume the conversation** (the same Codex thread, with everything it remembers) or **Start a new session** (a new thread in the same working copy, told what was asked, what is already changed and how many clips were delivered). The idle time is 30 minutes; for tests `AMPLE_AI_SESSION_IDLE_S` shortens it. So you can adjust without starting over: type in the message row of the proposal window, or in the bar of the read-only preview ("too loud" > listen > "make it 20% quieter"). Each message is a new turn on top of the proposal as it is now; the proposal (changes, checks, waveform) is updated and the preview builds and plays it again at once.
- **Steering while it works:** a message sent while Codex is working goes to it at once (`turn/steer`), it does not wait for the end.
- **Fast by instruction:** Codex is told to work quickly and focused, to read with one `ample_batch` call instead of many, to change as little as needed, and to answer follow-up messages quickly. The default model is the fast one (GPT-6-Luna).
- **`ample_batch`:** many read tools (project, docs, block types, song, block, file, analyse, check) in one request, in order, with their answers together (at most 12 calls).
- **Delivery without new problems:** Codex has `ample_check`, which lists errors and warnings that the song did not have before, and is told it is not finished until that is empty. AMPLE checks too: if the result has new errors or warnings it sends Codex back to fix them (at most twice) before you see the proposal; the proposal window says when that happened. Problems the song already had are not held against the proposal.
- **The thinking bubble** is fed by the tool `ample_thinking` and also by the summary of the model's reasoning when Codex gives one, so it moves even when Codex does not call the tool.
- API: `POST /api/ai/tasks/{id}/message`, `GET /api/ai/context/check`.

## Links the user gives, and a preview that waits

- **Codex has no network** (its sandbox is closed on purpose), so a link in the request (an image, an SVG, a page) used to fail with "the download was refused". AMPLE now fetches it for Codex with the tool `ample_fetch_url`: a link that is in your request or in one of your messages is downloaded at once; any other link first asks you ("Codex asks AMPLE to download a web address for it"). The file lands in `assets/web/` of the temporary copy (never in the proposal); text, SVG and JSON also come back as text. Only the public internet (never this computer or your local network, also not after a redirect), images, text, audio, JSON, XML and PDF, at most 10 MB.
- `ample_web_search` lets Codex choose between DuckDuckGo's free Instant Answer API and Brave's full web-search API. AMPLE persists only an API-key hash, UTC month and its own Brave request count under the library home, estimating remaining out of 1,000 calls; this is not the live Brave credit balance and does not include calls made elsewhere. Brave is capped at 10 actual calls per Codex turn and spaced by at least one second. Identical Brave query/count/offset calls can reuse a five-minute memory-only cache; results are not persistently cached. Brave's headers are not treated as a credit balance. `ample_web_read` can read a user-supplied or approved-search-result page without another approval, cookies or JavaScript; if that fails, the browser remains the fallback. AMPLE asks before each search, never silently switches provider, and does not scrape a search results page when an API returns nothing or fails.
- **The tools of AMPLE are accepted when Codex asks before calling them** (in Manual mode Codex asks for every tool that is not read-only); other MCP servers stay declined.
- **While Codex works again or a new build runs**, whatever was playing stops, the preview (the player, the ▶ of the blocks, Build and listen) is disabled, and the bar says why ("a new build of the proposal is in progress"). It comes back, with the new proposal, when the build is ready. Messages can still be sent in that time: they steer Codex.

## Editing with a tool instead of shell hacks

Codex used to change songs with PowerShell text replacements and regular expressions (fragile, and the first attempt often failed). It now has `ample_edit`: structured edits of a file of the temporary copy, all or nothing. The ops: `replace` (exact text; when it occurs more than once, use `occurrence` to select one match or `all` to replace every match), `insert` (after / before a line, or at a line number), `delete_lines`, `set_param` (sets or adds a parameter line of a block, for example `gains`), `add_block`, `remove_block` (it says which blocks still use it), `connect` and `disconnect` (a `from` line), and `create` (a new file). The first edit that does not fit stops the call and nothing is written; the answer lists the new errors and warnings and a diff, so Codex can fix them with the next call. Files with Windows line endings keep them; only files of the proposal can be edited (never `.ample`). The instructions tell Codex to use it instead of shell text replacement.

## Build progress of a proposal

While the build check runs (first check, a rebuild after a message, or a build you ask for) the proposal window and the preview bar show the same steps as the real build: *Checking the build* with a spinner, the number of blocks done of the total, a progress bar, and the blocks being made right now with their steps and how far they are (\`build.progress\` in the task).

## Checking its own work

When Codex thinks it is done it is told to check itself before it answers: read back what it changed and compare it with every part of the request, run \`ample_check\` (it must say ok), and, when the change can be heard (levels, gains, effects, notes, tempo, which sounds are used), run **\`ample_listen\`**. Codex cannot hear, so this builds its proposal in a temporary project and measures a block (or the master) with the analysers (loudness and spectrum by default; tempo, key and pitch too), next to the same block of the current project, so "20% quieter" can be seen as about -2 dB. It says what it measured in its answer. Changes that only touch comments or text need no listening. The reading tools (\`ample_file\`, \`ample_song\`, \`ample_block\`) show Codex its own proposal, not the unchanged project, so a read-back after an edit shows the edit (before, it showed the old text and Codex thought the edit had failed). \`ample_analyze\` measures the current project, not the proposal.

## When the proposal does not build, and a valid format first

- **Why it does not build, in detail.** For every block that failed, Codex gets the message and its code, a hint (from the diagnostics documentation when the code is explained there, else where to look: the block type and the block itself), what feeds the block, and the text of the block. The tool \`ample_build\` (optionally for one block) builds the proposal and answers with exactly that; \`ample_listen\` does the same when it cannot build. Errors in the song itself come back as lines with the hints of the parser. The same details are in the task (\`build.details\`).
- **A last gate before you see it:** after the format check, AMPLE builds the proposal; if it does not build, Codex is sent back once with those details and told to fix it. Only then the proposal is shown (with the result of its own build).
- **The format is checked first, for every file Codex changed:** \`ample_check\` (and AMPLE after the answer) checks the song with the parser (new errors and warnings, with their hints), a sequence file (\`.seq\`, \`.ampleseq\`) with the sequence parser, and JSON files for valid JSON. A file that was already invalid before the task is not held against the proposal. Codex is told to run it before it delivers.

## More information when Codex needs it (units, ranges, impact)

- **Every parameter says what it is.** \`ample_block_types type=<id>\` gives each parameter with its unit, minimum, maximum, step, default, how to write a value (for example \`-3 dB\`, \`25%\`, one of a list) and what it does. The list of all block types shows what each type takes and gives (\`in\`, \`out\` with their kinds), so Codex sees what can be connected.
- **\`ample_lookup\`** for more, on request: \`units\` (what dB, %, ms, s, Hz, bars, LUFS mean, how time and seeds work, and how "x% quieter" converts to dB: 20% is about -1.9 dB), \`parameter\` with \`type.parameter\` (unit, range, how to write it, what a change reaches), \`impact\` with a block of the song (what feeds it, what is rendered again when it changes, the files it reads, whether it reaches the master) and \`search\` with a word (block types, parameters and documents that mention it). It also works inside \`ample_batch\`.

## Checking the goal: arrangement and real length

\`ample_arrangement\` gives Codex the arrangement of the song **before** the task and **now**: tempo and bar length in seconds, where every block that reaches the master sits (bars and seconds), blocks that are not placed or do not reach the master, the slice of the master, the length of the arrangement from the text, and a list of what changed (added, left, moved or resized, tempo, slice). Without \`measure=true\`, it calculates planned duration without rendering. With \`measure=true\` it also builds the proposal and returns the **real** facts of the built master next to those of the current project: length in seconds, peak (dBFS) and the silence at the start and the end (below -60 dBFS counts as silence). \`ample_listen\` and \`ample_build\` return the same audio facts. \`ample_build\` accepts \`forceRender=true\` for one named ACE song/voice block when the user explicitly wants a genuine fresh render; it skips both AMPLE's exact-plan take cache and Faer's remote render cache. Ordinary matching ACE requests use Faer's bounded render cache automatically. When the user requests an output duration or range, Codex must use the non-rendering calculation first, adjust the master slice for a time-limited sample or the arrangement when the song itself should be shorter, and verify the planned seconds are in range before the first expensive render. \`measure=true\` is for checking actual rendered duration after this preflight, since it builds the proposal. This measures output duration, not render wall-clock time.

## Hum a melody

Say it with your voice when notes are hard to describe. **● Hum a melody…** is in the AI prompt (and in the message row of a proposal, and in the bar of the preview), in the **piano roll** (**● Hum…**: the notes go into the clip) and in the recorder of the arrangement (**→ melody**: a new midi-clip with the notes).

1. A count-in at the tempo of the song, then you hum, sing or whistle one line on one vowel, close to the microphone.
2. AMPLE finds the notes in it (the pitch of every moment, cut into notes) and shows them on a small roll, with the key that fits best. It is **an attempt**: a hummed line is never exactly in tune or in time. You hear the notes next to your own hum and can change the tempo, how fine the notes snap in time (sixteenth, eighth, beat, as sung) and whether they snap to a key (the best fitting one, or one you choose).
3. Only when you approve it, it is handed on. For Codex: *"Approve and give it to Codex"* keeps the recording on the server, shows it as a chip (♪ 6 notes, D minor) with your message, and Codex gets the **raw audio** (\`assets/hum/<id>.wav\` in its working folder) and the tool **\`ample_hum\`**: the notes with pitch names, the key and the \`notes\` text of a midi-clip at the tempo of the song (bar 1 or the start bar you gave). Codex can ask again with another \`tempo\`, \`grid\`, \`key\` or \`bar\`, and is told to check the attempt against your request and say how sure it is.

API: \`POST /api/hum/transcribe\` (WAV bytes; \`tempo\`, \`grid\`, \`key\`, \`bar\`), \`POST /api/ai/hum\` (keeps a recording, answers with its id), \`hums: [id]\` on a task or a message. The finder is built in (the YIN pitch method, no model or network needed): 16-bit WAV, mono or stereo, up to two minutes. Not covered: chords, several voices at once, or a noisy room.

## Offering sounds to Codex (drag, pick or record)

Give Codex material without putting it in your project first. In the AI prompt, the message row of a proposal and the bar of the preview you can **drag a sound onto the window**, **＋ Add audio…** (wav, mp3, ogg, flac) or **● Record a sound…** (the microphone). Each one shows as a chip you can listen to (▶) or remove (×). The files are only kept for this task (\`.ample/ai/attachments\`, removed after three days).

- **What Codex gets:** every offered file exists in its copy at \`samples/offered/<name>.wav\`, so a block can use it like any sample (\`file samples/offered/kick.wav\`), and the checks, the build check and \`ample_listen\` find it; the raw file is also in \`./assets/offered/\`. The tool \`ample_offered\` says what each one is (length, sample rate, peak and average level, silence at the ends, the pitch when there is one clear note) and whether the proposal already uses it. Codex is told to say in its answer which ones it used.
- **At Accept you decide what comes along.** The proposal window lists *Audio you offered Codex*: the files the proposal **uses** are ticked and have to come along (otherwise the song would not find them, and Accept refuses with AMP5463), the others are unticked and optional; every one can be heard first. Only the ticked ones are copied into the project (\`samples/offered/\`); **Undo** takes them away again. Nothing offered is in your project before you accept.
- API: \`POST /api/ai/attachment?name=\` (WAV bytes, or \`&extension=.mp3\` etc.), \`offered: [id]\` on a task or message, \`include: [id]\` on accept.

## Trying a variant, and reading without repeating

- **Hear a variant without changing the proposal.** \`ample_listen\` and \`ample_build\` take an optional \`edits\` list (the format of \`ample_edit\`, plus \`path\`): they are applied only in the temporary project of that call, so Codex can compare "-9 dB or -15 dB?" and then apply the one it chooses. (A change that does not move the measured number, as the kick channel did in the test, shows that the metric of the whole block is blunt for a single channel.)
- **Re-reading is answered shortly while nothing changed.** Codex re-reads blocks and files a lot after every round. When the same song, block or file is asked for again and nothing in its working folder (or the offered audio) changed since the last read, the answer is a short "unchanged since your last read"; once it changed something (a file is newer, bigger or new) the next read is fetched again with the change included.

## Memory of earlier requests, and how-tos

- **The AI remembers what you asked before.** Every request is written down in \`.ample/ai/history.jsonl\` when it is ready, accepted, rejected or failed (the request, what Codex said, the files it changed and, as far as kept, the changes; at most the last few hundred), so it survives a restart of the server. Codex gets the three latest requests on the same song with its first message and has the tool \`ample_history\` (newest first; \`id=<id>\` gives one in full with its changes) for "like before", "continue", "undo that last thing".
- **Continue an earlier request.** The AI prompt has a list of earlier requests of this song: pick one and its prompt comes back to tweak, and Codex is given that request, its answer and its changes (and told to check what is in the song now). A result without changes has a button **Continue this request…**. API: \`GET /api/ai/history\`, \`continueFrom\` on a task.
- **Project and song notes for later tasks.** \`ample_memory_read\` reads the project notes or the notes for the current song; \`ample_memory_write\` appends a dated note by default or replaces the whole note with \`mode=replace\` (empty text clears it). A single write is limited to 6,000 characters and each memory to 24,000. They are stored under \`.ample/ai/memory/\`, outside the working copy and song exports.
- **How-tos for what is not a plain parameter.** \`ample_lookup topic=howto query=<word>\` gives, in code-accurate form, how to change a value over the song (\`auto(bar:value,…)\`, \`lfo\`, \`env\`, \`fadein\`/\`fadeout\`, which parameters accept it: volume gain, the mix of delay, reverb, chorus, flanger, phaser and bitcrusher, compressor threshold, filter cutoff, pan; bars to seconds), fades, speed and tempo (the tempo is constant and not automatable; stretch.speed accepts auto(bar:percent, ...) for gradual ramps; project tempo remains constant), placing and cutting, sidechain and adding an effect, and says what is NOT possible with the closest workable alternative. \`topic=diagnostic\` explains an error code with a wrong and a right example, and \`search\` also finds how-tos. \`ample_edit\` also has targeted transpose, velocity and quantize operations for compact MIDI notes.

## Letting the user hear a block (clips)

Codex can **present sound** with \`ample_present\`: the render of a block (empty: the master; \`block.port\` for one output such as a sequencer lane), either a musically useful **slice** (\`from\`/\`to\` in seconds, or in bars with \`unit=bars\`) or the full render when requested or useful for comparison, as the **proposal** has it (the default) or as the **current project** is. The requested range is preserved without a 90-second cap; a full-song request is not silently truncated. A few milliseconds of fade are applied at both ends of a slice. It appears in the task window, also while Codex is still working, as a card *Codex wants you to hear*: label, which block, whether it is the proposal or the project as it is now, the range, why it is shown, a waveform player, and quick answers (*Yes, that is it*, *No, another one*, *Play me more of it*) that fill the message box. Ctrl+click (or Meta+click) on one of those choices sends its action immediately and includes the sample and block references in the message. Codex is told to use it when it is not sure which instrument or part you mean (present the candidates and say which it chose), to let you compare before and after, and to let you check a result.

Codex alone marks samples obsolete and supplies the reason; the user can hide a card with × and undo that hide with Ctrl+Z. When Output is open, its content is the only vertical scroller; the task body and tabs stay fixed.

What was presented is **remembered**: each request in the history keeps the label, block, source, range and reason of its clips (\`ample_history\`), so later you can say "I think you are modifying the wrong instrument, play me what you think I mean" and Codex can find what it had presented and present it again. The audio files are kept for the session (\`.ample/ai/clips/<task>\`), the information stays in the history. API: \`GET /api/ai/tasks/{id}/clip/{clip}\`.

## Requests for a Flemish sound

When a request asks for music to sound more Flemish, Codex is guided to treat that as an open direction rather than a single genre or a caricature. It should follow details the user gives, avoid inventing dialect, and consider whether the request concerns Flemish Dutch wording/prosody, a local or traditional feel, contemporary Flemish music, or another quality. When the intended direction is open to interpretation, it can offer a few musically distinct short variants with `ample_present`, explain their differences, and let the user choose. Codex may also offer extra iterations as an option—for example, explore contrasting directions, compare them, then refine the chosen one. Extra rounds are optional and should help resolve an open direction; they are not added to narrow requests and do not guarantee a more Flemish result.

In a finished proposal, Codex's written summary is part of the scrollable **Output** content, below the fixed tab row, so opening Output does not shift the tabs vertically.

## Assistant tab sessions

The bottom **Assistant** tab stores named conversations in the open project's `.ample/ai/assistant-sessions/` folder. The index keeps each session title and task references; task snapshots and the bounded activity log are stored beside it. Project switching therefore loads a different session index. Create, rename and delete are available in the tab; a session with a live task or an unapplied proposal cannot be deleted.

Assistant task outcomes are also written to AMPLE Redux, including redacted request/summary metadata, proposal change counts and hashes for content-addressed before/after text, plus presented audio clip hashes and render settings. Full conversation capture is **off by default**. When creating a session or from its archive control, it can be enabled for new messages; an additional explicit choice can import earlier messages still available for that session. Captured text is redacted for common credential patterns before it enters Redux. Existing task-log files may contain earlier conversation text, but the Assistant view hides those messages while capture is off.

The Health page shows aggregate AMPLE Redux storage use. The default 10 GiB budget warns at one fifth (2 GiB); changing the project budget changes both thresholds proportionally. **Preview compaction** shows the exact segment, record, summary and byte impact; compaction then requires a separate confirmation. Records are never pruned automatically.

Starting from the tab opens the same full prompt and proposal interface as other Codex entry points. The task keeps the session ID, while existing task APIs remain usable; callers that omit it receive an automatically named session. The session list opens its newest task and exposes earlier requests in the same conversation.

Codex threads are started as persistent app-server threads. After a server restart, the task snapshot and temporary project copy are retained. The task appears as interrupted and offers **Resume conversation**, which reconnects with `thread/resume` and registers the AMPLE MCP server at the current server URL. A task stopped with **Stop now** can also resume when it already has a saved thread; it reconnects to the same conversation and leaves the proposal unaccepted until you continue or accept it. Tasks cancelled before Codex starts a thread offer **Ask again** instead. The proposal remains unaccepted if the thread cannot be resumed. Runtime recovery still depends on Codex retaining that thread and the temporary work directory remaining available.

**Accept selected & continue** is available for one or more checked proposal files when the task is ready, not stale, and its complete proposal build succeeded. AMPLE validates the selected text, checkpoints the project, journals non-song writes, updates the accepted baseline, and then sends the supplied continuation instruction into the same Codex thread. Remaining files stay proposed in the temporary project. If the follow-up fails, already accepted files remain in the project and the task shows the failure; no remaining files are accepted automatically. API: `GET/POST /api/ai/sessions`, `PATCH/DELETE /api/ai/sessions/{id}`, `POST /api/ai/tasks/{id}/resume`, and `POST /api/ai/tasks/{id}/accept-selected-continue`.

## Moves that Codex proposes (2026-10-10)

Codex can propose moving or renaming a project file or folder (a sample, a module, a song, a whole folder) with the tool `ample_move`. A move is **never made in the temporary copy** (it holds only the files in scope, not your audio or your other songs): it is made at **Accept**, after the file changes, one by one, with every path in the songs and modules that points at it following (the same refactor as Move in the project panel). Codex chooses how:

- **`confirm: "ask"`**: you get an approval card now (*Codex asks to move a file or folder*) and Codex waits for your answer. *Approve the move* records it as approved, *Deny* tells Codex, which goes on without it. Codex uses this when the rest of its work depends on the move. In **Unsafe / Auto-all** mode there is no question.
- **`confirm: "propose"`** (the default): the move is listed under **Moves Codex proposes** in the proposal with a checkbox, the number of lines in your songs that will follow, and the reason. Ticked moves are made at Accept; nothing moves before.

Refused when it is proposed: a source that does not exist, a destination that exists (a move never overwrites), a folder into itself, `.ample`, the song of the task itself, or a path that is already part of another proposed move. A move is skipped at Accept (with a note in the log) when a song that would have to change has unsaved changes, or when the source is gone or the destination exists by then. **Undo** puts accepted moves back, the references following again. *Accept selected* (and *Accept selected & continue remaining*) make the approved and the ticked moves too, after the checked files; a move that is not ticked stays in the proposal.

The separate tool `ample_move_file` moves a text file inside the staged proposal without overwriting. Its source and destination are project-relative; `workspace/<filename>` can recover a misplaced text file from the working-copy root. It changes no live project file before Accept. Use `ample_move` for a project file or folder whose references need to follow the move.

The tool `ample_copy_file` (2026-10-14) copies a text file inside the staged proposal to a new, not-yet-existing path; unlike `ample_move_file` the source stays in place. Use it to duplicate a sequence or module before changing the copy, so other songs that still point at the original are unaffected — for example giving one song its own patched copy of a sequence that other songs also use. A `workspace/<path>` source instead stages a file `ample_fetch_url` downloaded into `assets/web/` of the working folder (an image, a PDF, a fetched score) into the project, since nothing else can move a fetched asset out of the working folder and into the proposal.

`ample_import_score` (2026-10-15) also accepts a staged PDF or image of printed music, recognized with Audiveris (optical music recognition) when it is installed, and a MuseScore/Guitar Pro/Capella/Overture file or a zipped `.mxl`, converted with MuseScore (or unzipped directly for `.mxl`) — see `docs/score-import.md`. The typical flow for a score found on the web: `ample_fetch_url` to download it, `ample_copy_file` with a `workspace/` source to stage it into the proposal, then `ample_import_score` on the staged path. OMR can misread a source, so the tool's answer says to check the note count before trusting it; a MuseScore/.mxl conversion is a faithful machine conversion, not recognition.

API: `POST /api/ai/context/move` (for the tool), `moves: [id]` (the ticked ones) on `POST /api/ai/tasks/{id}/accept`, `accept-selected` and `accept-selected-continue`, `moves` in the task JSON. `ample_copy_file` posts to `POST /api/ai/context/copy-file`.

## Variants (several alternatives in one proposal)

When the request is for several alternatives of one thing (three instruments for a phrase, other beats), the model makes all of them in the one temporary copy, each as its own blocks, and calls the MCP tool `ample_offer_variants` once: for every variant a `name`, a one-line `summary`, the `blocks` that belong to it and the `listen` block (the end of its chain). The task then carries `variants`. Koda shows them as A, B and C: a variant is the proposal with only its own blocks (the changes that belong to no variant are in all of them), each can be listened to on its own (only its `listen` block is built, from the proposal), the block as it is now can be played to compare, and "Use this one" puts only that variant in the song as one undo step. Nothing is recognised from the words of the request: the model offers the variants through the tool.

## Resuming a session after hours (2026-10-23)

A session keeps its working copy and its Codex conversation for **24 hours after its last use** (a Koda question for one hour), also after Accept or Reject, as long as the copy is not bigger than 500 MB. In that time the assistant tab can resume it ("Resume conversation"): the same Codex thread is reopened in the same copy. The first turn after a resumption starts with an AMPLE NOTE: how long ago, what happened to the last proposal (accepted, rejected, undecided) and which files of the copy differ from the project now. The tool `ample_changes_since` lets the model look further: no arguments gives the overview, `path` the diff of that file (what the copy was based on against the project now), and `path` with `import=true` brings the project's version into the copy, merged with the model's own edits (a clash is reported, never guessed). Koda uses the same thread resume for **Hang around**, with the song brought up to date by the normal preparation.
